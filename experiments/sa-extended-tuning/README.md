**นี่เป็นการจูนเพิ่มหลังเห็นผล ไม่ใช่ผลหลัก** [`docs/protocol.md`](../../docs/protocol.md) กำหนดว่าจะไม่ขยายช่วงหลังเห็นผล ผลหลักจึงยังเป็น [`experiments/final/`](../final/) ส่วนนี้ทำเพื่อตอบข้อสังเกตของอาจารย์ว่า ค่า SA ที่เลือก (`initial_acceptance` 0.2, `cooling_rate` 0.9) อยู่ที่มุมของ grid เดิม การที่ GA ดีกว่า SA จึงอาจเป็นเพราะจูน SA ไม่พอ

รันเมื่อ 2026-11-14 ด้วย engine C# (ผลตรงกับ Python ทุกบิต engine SHA-256 `e9222d73…` เดียวกับ [`../engine-speed/final-csharp/`](../engine-speed/final-csharp/)) บน Linux 4 คอร์

## ขั้นที่ 1: ขยาย grid บน seed จูน 1–10

ทุกชุดจัดครบทุกคาบในทุก seed จึงตัดสินด้วย Lab ไม่จำเป็น ค่าที่ดีที่สุดคือ **0.01 / 0.8 (54.9 ชม.)** ดีกว่าค่าเดิม 3.5 ชม. และ cooling 0.8 อยู่ด้านในของช่วงแล้ว ส่วน acceptance 0.01 ยังอยู่ใกล้ขอบล่าง แต่เมื่อลองลดลงไปที่ 0.001 ผลไม่ดีขึ้น (ดีสุด 56.5) และ acceptance เข้าใกล้ 0 ก็คือ SA ที่ไม่ยอมรับคำตอบแย่ลงเลย ซึ่งทำงานแบบเดียวกับ hill climbing จึงไม่มีช่วงให้ขยายต่อในทิศนั้นแล้ว

**ผลไม่เรียบ:** ชุดที่ติดกันใน grid ต่างกันได้มาก เช่น 0.01 / 0.8 = 54.9 แต่ 0.01 / 0.7 = 78.3 และ 0.01 / 0.9 = 73.8 แปลว่าความต่างระหว่างชุดค่าส่วนใหญ่มาจากความแปรปรวนระหว่าง seed (ส่วนเบี่ยงเบนมาตรฐานต่อรันราว 20 ชม.) มากกว่าจากตัวพารามิเตอร์

## ขั้นที่ 2: รัน SA ค่าใหม่บน seed ทดสอบ 1001–1030

SA 0.01 / 0.8 × seed 1001–1030 × โหมด weekly และ fixed = 60 รัน แล้ววิเคราะห์ร่วมกับ Greedy, HC และ GA ชุดเดิมจาก `experiments/final/` (`combine.py` แทนที่เฉพาะรันของ SA แล้วส่งให้ `engine/analyze.py`)

| | SA ค่าเดิม (0.2 / 0.9) | SA ค่าใหม่ (0.01 / 0.8) |
|---|---:|---:|
| Lab ไม่จำเป็นเฉลี่ย, weekly (ชม.) | 76.2 | 77.5 |
| seed ที่ค่าใหม่ดีกว่า / แย่กว่า | – | 15 / 15 |
| อันดับเฉลี่ย Friedman (GA / HC / SA / Greedy) | 1.53 / 1.93 / 2.53 / 4.00 | 1.63 / 2.03 / 2.33 / 4.00 |
| GA vs SA (Wilcoxon, Holm) | GA ดีกว่า 26/30 seed, p < 0.001 | GA ดีกว่า 23/30 seed, **p = 0.003** |
| HC vs SA | ไม่ต่าง (p = 0.176) | ไม่ต่าง (p = 0.128) |
| HC vs GA | ไม่ต่าง (p = 0.188) | ไม่ต่าง (p = 0.188) |

ตารางและสถิติเต็มอยู่ใน [`analysis/report.md`](analysis/report.md) (คอลัมน์เวลาค้นหาของ SA ในไฟล์นั้นมาจาก C# ส่วนวิธีอื่นมาจาก Python จึงเทียบเวลากันไม่ได้)

## สรุป

- ค่าใหม่ที่ดีกว่าบน seed จูน **ไม่ได้ดีขึ้นบน seed ทดสอบ** (76.2 → 77.5 ชม. ชนะ 15 แพ้ 15 seed) การจูนเพิ่มจึงได้แค่ค่าที่บังเอิญเข้ากับ 10 seed นั้น
- **ข้อสรุป "GA ดีกว่า SA อย่างมีนัยสำคัญ" ยังอยู่** หลังจูน SA เพิ่ม (p = 0.003) และข้อสรุป "GA กับ HC แยกกันไม่ได้" ก็ไม่เปลี่ยน
- ผลหลักและตัวเลขในสไลด์จึงยังใช้ชุด `experiments/final/` ได้ ส่วนข้อจำกัด "SA อยู่ขอบช่วงที่จูน" เปลี่ยนเป็น "จูน SA เพิ่มแล้ว ผลไม่เปลี่ยน"
- ที่ SA ดีสุดเมื่อทำตัวใกล้ hill climbing เข้ากับข้อสรุปของ Abdipoor et al. (2025) ใน [`docs/research-comparison.md`](../../docs/research-comparison.md) ว่าที่งบน้อย วิธีที่เน้นปรับคำตอบใกล้ตัวทำได้ดี

## ไฟล์และการรันซ้ำ

| ไฟล์ | เนื้อหา |
|---|---|
| `run.sh` | ขั้นที่ 1 (รันซ้ำจะข้ามชุดที่มีผลแล้ว) |
| `configs/<id>/` | ผลดิบของแต่ละชุด (`experiment.csv`, `experiment.json.gz` แบบ slim, `manifest.json`, `parameters.json`) |
| `summary.csv`, `summarize.py` | ค่าเฉลี่ยต่อชุด (ตารางขั้นที่ 1) |
| `selected-sa.json` | ค่าใหม่ 0.01 / 0.8 |
| `test-seeds-sa/` | ขั้นที่ 2: SA ค่าใหม่ 60 รัน (ผลเต็ม) |
| `combine.py`, `analysis/` | ผลวิเคราะห์ร่วมกับ Greedy / HC / GA ของ `experiments/final/` |

```sh
bash experiments/sa-extended-tuning/run.sh
python3 experiments/sa-extended-tuning/summarize.py
dotnet run -c Release --project dotnet/src/Timetabling.Cli -- batch run --methods sa --room-modes weekly fixed \
  --seeds 1001-1030 --budget 500 --parameters experiments/sa-extended-tuning/selected-sa.json \
  --output experiments/sa-extended-tuning/test-seeds-sa
python3 experiments/sa-extended-tuning/combine.py /tmp/combined.json.gz
python3 engine/analyze.py /tmp/combined.json.gz --output experiments/sa-extended-tuning/analysis
```
